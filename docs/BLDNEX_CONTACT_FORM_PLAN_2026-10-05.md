# BLDNEX 사이트 직접 접수형 문의 폼 구현 계획

작성일: 2026-10-05 · 상태: 계획 수립 / 구현·외부 설정 변경 전

후속 상태: 사용자의 구현 승인으로 로컬 구현·검증을 진행했습니다. 이 문서는 계획 당시 기록이며, 최신 적용 범위와 미확정 운영값은 [문의 구현·운영 연결 초안](BLDNEX_CONTACT_IMPLEMENTATION_2026-10-05.md)을 우선합니다. 실제 접수는 아직 비활성이고 이번 변경은 미배포입니다.

사용자 요청: “사이트에서 바로 접수로 구현하기 위한 계획 수립”.
이 문서는 메일 앱을 여는 입력 보조 폼이 아니라, 웹사이트 안에서 접수 결과까지 확인하는 정식 문의 기능을 계획합니다. 계획 작성은 서비스 가입·DNS 변경·유료 사용·프로덕션 배포 승인을 뜻하지 않습니다.

## 1. 현재 상태와 권장 방향

최신 저장소의 [배포 기록](wiki/deploy.md), [구조](wiki/architecture.md), `wrangler.toml`, `src/data/privacy.ts`를 기준으로 합니다.

- Astro 정적 사이트는 Cloudflare Pages에 배포된 것으로 기록되어 있습니다. 호스팅·도메인·기존 페이지는 유지합니다.
- Contact는 이메일 링크/복사 방식이며 접수 API, DB, 메일 발송 연동, 문의 관리 화면은 없습니다.
- 개인정보 설정에는 담당자·주소·보관 기준·시행일 값이 있습니다. 다시 빈 값으로 취급하지 않습니다. 다만 현재 본문은 “폼/DB 없음”을 전제로 하므로 정식 폼에 맞게 수정·검토해야 합니다.
- 기존 보관 기준은 “문의 처리 종료 후 1년”입니다. 폼으로 수집한 정보에도 같은 기준을 적용할지 확인하고, 미종결 문의의 보관 종료 기준도 정해야 합니다.
- 브랜드 SVG, 폰트, 반응형 디자인, URL 형식, 셀프호스팅 폰트는 유지합니다.

**권장 구성: 기존 Pages + Pages Functions + D1 + Turnstile + Resend + Cloudflare Access.**

초기 기획의 독립 Worker API 대신, 기존 Pages 프로젝트의 같은 도메인에 `/api/contact`를 붙이는 것을 제안합니다. Pages Functions는 Workers 런타임에서 폼 처리 서버 코드를 실행하고 D1 바인딩을 사용할 수 있어, 현재 정적 사이트를 SSR로 바꾸지 않아도 됩니다. 이는 기존 배포 구조에 맞춘 설계 제안입니다. [Functions 공식 문서](https://developers.cloudflare.com/pages/functions/), [바인딩](https://developers.cloudflare.com/pages/functions/bindings/)

정기 알림 재시도와 보관 기간 만료 처리는 D1을 공유하는 작은 예약 실행 Worker로 분리합니다. 사이트 전체의 Workers Static Assets 이전은 이번 범위에 넣지 않습니다. [Cron Triggers](https://developers.cloudflare.com/workers/configuration/cron-triggers/)

## 2. 1차 구현 범위

### 방문자

- 기존 Contact 안에 프로젝트 문의 폼 배치. 데스크톱은 폼 + 준비 안내, 모바일은 한 열.
- 프로젝트 유형 → 문의 내용·예산·일정 → 회신 정보 → 개인정보 안내/동의 → 보내기 순서.
- 잘못된 입력 안내, 첫 오류로 포커스 이동, 설명 글자 수, 전송 중 중복 클릭 방지.
- 저장이 확인되면 접수번호와 완료 안내를 표시.
- 실패 시 입력값 유지. 네트워크 단절처럼 결과가 불확실하면 중복 없는 확인·재시도 흐름 제공.
- 이메일 문의와 주소 복사는 보조 연락 경로로 유지. JavaScript나 보안 확인이 동작하지 않을 때도 이메일로 문의 가능.

### 운영자

- 관리자 전용 문의 목록·상세·상태 변경.
- 신규 / 검토 중 / 연락 완료 / 종료 상태와 종료 시각.
- 알림 실패 표시와 재발송, 승인된 파기 기준에 따른 삭제.
- 새 문의는 DB 저장 후 기존 대표 이메일로 알림.

### 1차에서 제외하는 항목 — 제안

- 첨부파일 업로드와 R2: 파일 검사·비공개 다운로드·파기 범위가 늘어나므로 후속 단계로 분리. 자료는 본문 참고 링크나 후속 이메일로 받습니다.
- 고객 계정, 고객용 문의 조회/답변 게시판, 자동 견적, CRM 연동, 고객에게 보내는 자동 회신.
- 추적용 분석·광고 도구.

## 3. 폼 필드와 문구

| 항목 | 필수 여부 | 입력·검증 기준 |
| --- | --- | --- |
| 프로젝트 유형 | 필수 제안 | 웹사이트 / 웹앱·SaaS / 모바일 앱 / 기타·상담 필요 |
| 이름 / 담당자명 | 필수 | 공백 정리 후 2~50자 |
| 회사 / 팀 이름 | 선택 제안 | 최대 100자. 개인은 비워둘 수 있음 |
| 회신받을 이메일 | 필수 | 이메일 형식·길이 검증, 헤더 제어문자 차단 |
| 연락처 | 선택 | 비어 있으면 허용, 입력 시 길이·허용 문자 검증 |
| 예상 예산 | 필수 | 협의 필요 / 1천만 원 미만 / 1천만~3천만 원 미만 / 3천만 원 이상 |
| 희망 일정 | 필수 | 미정 / 1개월 이내 / 1~3개월 / 3개월 이후 |
| 프로젝트 설명 | 필수 | 공백 정리 후 20~5,000자. 참고 링크는 텍스트로 입력 |
| 개인정보 수집·이용 동의 | 필수 | 기본 미선택. 고지 버전과 서버 접수 시각 기록 |

예산은 견적 약속이 아니라 상담 준비 정보입니다. 선택정보의 수집·동의 구조는 실제 운영과 법률 검토에 맞추며, 선택정보를 제공하지 않아도 접수할 수 있어야 합니다.

기존 [원고 Q03/Q05](BLDNEX_WEBSITE_COPY_DRAFT_2026-10-03.md)를 재사용합니다.

| 설명 | 만들고 싶은 것과 현재 상황을 적어주세요. 구체적인 기획서가 없어도 괜찮습니다. |
| 보내기 | 프로젝트 문의 보내기 ↗ |
| 전송 중 | 문의를 보내는 중입니다… |

| 불확실 상태 버튼 | 접수 확인·재시도 |

응답 시간이나 영업일 내 회신을 임의로 약속하지 않습니다. 불확실 상태 버튼은 아래의 동일 요청 식별자 재시도를 구현한 뒤에만 노출합니다.

## 4. 접수·저장·알림 흐름

```text
방문자 입력
  → 브라우저 검증 + Turnstile
  → POST /api/contact
  → 서버 검증·요청 제한·중복 확인
  → D1에 문의 + 알림 대기 작업 함께 저장
       ├─ 저장 확인 → 접수번호 반환 → 완료 화면
       ├─ 관리자 → 인증 후 문의 확인·상태 처리
       └─ 알림 처리 → Resend → 대표 Gmail
                      실패 → 대기 작업 유지·예약 재시도·관리자 표시
```

**접수의 기준은 DB 저장입니다.** 이메일 서비스가 실패해도 이미 저장된 문의를 실패로 처리하거나 삭제하지 않습니다. 알림 발송용 대기 작업도 영속 저장해, 단순 백그라운드 호출이 중단되어도 다시 처리할 수 있게 합니다.

### 데이터 모델 제안

| 테이블 | 핵심 내용 |
| --- | --- |
| `inquiries` | 무작위 ID·접수번호, 요청 키/내용 해시, 입력값, 동의 버전/시각, 상태, 생성/수정/종료/파기 예정 시각 |
| `notification_jobs` | 문의 ID, 대기/처리 중/발송 요청 수락/재시도/실패 상태, 횟수, 다음 시도 시각, 처리 잠금 만료 시각, 제공자 메시지 ID |
| `admin_events` | 변경 종류·운영자·시각 중심의 최소 감사 기록. 문의 본문을 복제하지 않음 |

문의와 알림 작업은 D1의 배치 트랜잭션을 이용해 함께 반영하고, 중복 요청 키·알림 작업에는 UNIQUE 제약을 둡니다. prepared statement로 값과 SQL을 분리합니다. [D1 Database API](https://developers.cloudflare.com/d1/worker-api/d1-database/)

### 중복·네트워크 단절

- 브라우저가 문의 시도마다 충분히 긴 무작위 요청 키를 생성합니다.
- 동일 키·동일 내용이면 기존 접수 결과를 반환하고, 동일 키·다른 내용이면 충돌로 처리합니다.
- 버튼 비활성화만으로 중복 방지를 끝내지 않고 DB 제약으로 동시 요청도 막습니다.
- 서버 저장 후 응답이 유실되면 같은 키로 확인·재시도합니다. 신규 저장에는 유효한 Turnstile 검증을 요구하고, 이미 저장된 요청의 결과 확인은 일회용 토큰 재사용과 분리합니다.
- 익명 응답에는 접수번호/접수 여부만 반환합니다. 번호만으로 문의 내용을 조회하는 공개 API는 만들지 않습니다.
- 입력 내용은 현재 페이지 메모리에만 유지하고 기본적으로 localStorage에 저장하지 않습니다. 페이지 재접속까지 초안 복구를 지원하는 것은 별도 범위입니다.

### 이메일 알림

- 수신처: 기존 `BLDNEX.DEV@GMAIL.COM`.
- 발신처 제안: 소유 도메인에서 인증한 `notifications@notify.bldnex.com`. 주소·DNS 레코드는 설정 시 확정합니다. Gmail을 발신 도메인처럼 사용하지 않습니다.
- 메일 내용은 접수번호·시각·프로젝트 유형과 관리자 링크 중심으로 최소화합니다. 전체 문의 본문·전화번호를 메일함에 중복 보관하지 않는 안을 권장합니다.
- 알림은 원자적 작업 점유와 만료 가능한 잠금으로 동시 발송을 제어합니다. 재시도에도 같은 발송 키를 사용합니다.
- Resend의 중복 방지 키는 24시간 후 만료하므로, 자동 재시도 창을 그 이내로 제한하고 이후 수동 재발송에는 중복 가능성을 안내합니다. “API 발송 요청 수락”과 “수신함 배달 완료”는 구분합니다. [발송 API](https://resend.com/docs/api-reference/emails/send-email)
- 소유 도메인 인증과 요구 DNS 레코드는 Resend 공식 절차로 설정하며 기존 메일/다른 제품의 DNS를 덮어쓰지 않습니다. [도메인 설정](https://resend.com/docs/dashboard/domains/introduction)

## 5. 보안·개인정보·관리자

### 공개 API

- 서버에서 필수값·길이·선택지·동의 버전·Content-Type·전체 요청 크기를 검증합니다.
- 운영 호스트/Origin 허용 목록, 서버 측 요청 제한, 보조 허니팟을 적용합니다. CORS나 허니팟만으로 스팸을 막는다고 보지 않습니다.
- Turnstile은 서버에서 검증하고 hostname/action을 확인합니다. 토큰은 5분 유효·일회용이므로 만료/재시도 시 갱신합니다. [서버 검증](https://developers.cloudflare.com/turnstile/get-started/server-side-validation/)
- 오류에는 내부 SQL·키·개인정보를 노출하지 않습니다. 로그/분석에 이름·이메일·문의 본문·검증 토큰을 넣지 않습니다.
- API 응답은 `Cache-Control: no-store`. 정적 Pages의 `_headers`만 믿지 않고 Functions 응답에 필요한 보안 헤더를 직접 설정합니다. [Pages 헤더 적용 범위](https://developers.cloudflare.com/pages/configuration/headers/)
- 운영 설정이 빠지면 접수를 막고 이메일 경로를 제공합니다. 테스트 토큰·개발 모드로 운영 접수를 허용하지 않습니다.

### 관리자

- `/admin/inquiries`와 `/api/admin/*`는 Cloudflare Access 허용 계정만 접근.
- API에서도 JWT 서명·발급자·대상·만료와 허용 운영자를 검증합니다. 프런트엔드 로그인 여부나 헤더 존재만 신뢰하지 않습니다. [Access JWT 검증](https://developers.cloudflare.com/cloudflare-one/access-controls/applications/http-apps/authorization-cookie/validating-json/)
- 상태 변경·재발송·삭제는 인증과 CSRF 방어를 적용합니다.
- 문의 내용은 HTML로 실행하지 않고 텍스트로 렌더링합니다.
- `pages.dev` 및 미리보기 주소로 우회해도 운영 DB를 읽을 수 없도록 서버 인증·환경 분리를 검수합니다.
- 사이트 전체에 Access를 걸지 않아 일반 방문자의 문의를 막지 않습니다.

### 개인정보 — 공개 전 필수 검토

- `src/data/privacy.ts`의 “문의 폼 없음”, “DB 미운영”, “외부 전송 없음” 전제를 실제 동작에 맞게 바꿉니다.
- 웹 문의 필드, Cloudflare D1/Turnstile, 발송 서비스, 운영자 인증, 필요한 보안 로그의 역할·항목·기간·처리 위치를 확인합니다.
- 동의에 기반한 수집에는 목적·항목·보유 기간·거부권/불이익 안내를 연결합니다. 체크박스만 추가해서 고지를 끝내지 않습니다. [개인정보 보호법 제15조 제2항](https://www.law.go.kr/LSW/lsLinkCommonInfo.do?chrClsCd=010202&lsJoLnkSeq=1033214947)
- 기존 “처리 종료 후 1년” 기준의 폼 적용, 종료 시점, 미종결 문의, 별도 법정 보존 기록을 정리합니다. 이를 법정 의무 기간이라고 표현하지 않습니다.
- 예약 작업으로 만료된 문의와 관련 작업/기록을 처리합니다. 삭제 시 알림 작업을 먼저 취소하고, 백업 복구 시 이미 파기한 데이터가 다시 운영에 복귀하지 않도록 절차를 둡니다.
- D1만 삭제하면 모든 사본이 지워진다고 안내하지 않습니다. Gmail·발송업체·보안 로그·백업의 보관/파기 방식도 점검합니다.
- 기존 값이 모두 채워졌거나 noindex가 해제된다는 사실만으로 방침 검토 완료를 판단하지 않습니다. 공개 전 운영 주체 확인과 필요한 법률 검토를 거칩니다.

## 7. 구현 순서와 완료 기준

| 단계 | 작업 | 다음 단계로 넘어가는 조건 |
| --- | --- | --- |
| 1. 사양 고정 | 1차 필드/첨부 제외, 접수 기준, 개인정보·메일 서비스·관리자 계정 | 미정 항목과 운영 승인 범위가 기록됨 |
| 2. 폼 + 공통 검증 | 반응형 UI, 접근성, 오류/중복 클릭/입력 유지, 모의 API 테스트 | 화면·경계값·키보드 테스트 통과. 모의 성공을 운영 접수로 표시하지 않음 |
| 3. 실제 저장 | Functions, D1, Turnstile, 요청 제한, 중복 방지, 알림 대기 저장 | 로컬 DB에서 유효 문의 1회 저장 및 실패/경쟁 요청 검증 |
| 4. 운영 처리 | Resend, 예약 재시도, Access 관리자, 파기 작업 | 알림 실패해도 문의 조회 가능, 인증 우회 실패, 재시도/삭제 검증 |
| 5. 스테이징 | 별도 DB/키/수신처, 실제 이메일 전달, CSP·도메인·권한·정책 확인 | 아래 시나리오와 모바일 실기기 검수 통과 |
| 6. 공개 | 운영 승인 후 API/관리 기능 준비 → 개인정보 안내와 폼 활성화 → 실제 접수 확인 | 운영 DB 기록·대표 메일 수신·관리자 확인까지 대조. 테스트 기록 정리 |

핵심 검수 시나리오:

1. 정상 문의가 한 건 저장되고 접수번호와 관리자 기록이 일치.
2. 빈 값·잘못된 이메일·길이 초과·동의 누락·변조된 선택지는 서버에서도 거절.
3. 더블클릭/동시 요청/저장 직후 응답 단절에도 한 번만 저장.
4. Turnstile 만료·중복·외부 hostname, 요청 제한, 초과 크기 처리.
5. DB 장애에는 성공 표시 없음. 알림 장애에는 DB 기록 유지 및 재시도.
6. 비로그인/위조 JWT/다른 Access 앱 토큰/미리보기 우회로 개인정보 조회 불가.
7. 처리 종료·기간 만료·삭제 요청 후 알림 작업과 데이터가 다시 살아나지 않음.
8. 320/375/768/1280px, 키보드, 읽기 도구의 오류 안내, 느린 네트워크, JS/보안 스크립트 실패 시 이메일 대안.
9. 기존 `pnpm check`·`pnpm test`에 API/통합/E2E 검사를 추가. 기존 정적 페이지·홈 성능·폰트도 회귀 검수.

로컬 API 검수에는 Wrangler Pages 로컬 실행 환경을 추가합니다. `astro dev`만으로 Functions가 검증된 것으로 취급하지 않습니다.

## 8. 운영 연결에 필요한 선택·설정

| 항목 | 현재 기준 / 결정할 내용 |
| --- | --- |
| 메일 발송 서비스 | Resend 권장안. 사용 승인과 계정/발신 도메인 인증 필요 |
| 알림 수신처 | 기존 대표 Gmail 유지 권장 |
| 관리자 로그인 | 허용할 이메일 계정 확정. 수신 메일과 같아야 하는 것은 아님 |
| 개인정보 보관 | 기존 “처리 종료 후 1년”을 폼에도 적용할지, 미종결 문의 기준 확인 |
| 공개 범위 | 회사/연락처 선택, 첨부파일 후속 적용 승인 |
| 인프라 | D1 운영/스테이징 DB, Turnstile site/secret, Access 설정, API 및 예약 Worker secrets |
| 비용 | Cloudflare/Resend의 선택 요금제·한도·예산 알림 확인. 무료 운영을 전제로 약속하지 않음 |
| 공개 시점 | 개인정보 안내와 운영 검수가 완료된 뒤 사용자 승인으로 활성화 |

비밀 키는 채팅·원고·클라이언트 코드에 넣지 않고 Cloudflare의 비밀 설정으로 등록합니다. 계획 단계에서는 실제 가입·결제·DNS·인증 정책·운영 리소스를 변경하지 않습니다.

## 9. 장애 시 전환·롤백

- `CONTACT_ENABLED` 등 운영 스위치로 API의 신규 접수를 차단할 수 있게 합니다. 화면만 숨겨 API가 계속 받는 상태를 피합니다.
- 장애 동안 Contact는 기존 이메일 문의 경로로 복귀. 저장된 문의를 삭제하거나 이전 DB로 덮어쓰지 않습니다.
- 문의 저장과 알림 재시도의 상태를 별도로 살펴 신규 문의 유실/알림 실패를 구분합니다.
- 초기 마이그레이션은 추가형으로 작성해 기존 정적 사이트로 롤백해도 데이터가 남도록 합니다.
- 공개 후 저장 실패·알림 최종 실패·인증 실패·파기 작업 실패를 개인정보 없는 지표로 확인합니다. 확인 담당자와 점검 주기를 운영 문서에 기록합니다.
