## 1. 추천 방향

BLDNEX를 **“무엇을 만들지 함께 정리하고, 웹사이트·SaaS·앱으로 구현하는 제품 개발 스튜디오”**로 설명합니다. 방문자가 자신의 프로젝트를 맡길 수 있는지 판단하는 데 필요한 정보를 채웁니다.

지금 사이트는 브랜드 분위기는 있지만 서비스 이름, 짧은 제품 설명, 추상적인 작업 원칙 위주입니다. 다음 네 질문에 구체적으로 답하는 것이 이번 업데이트의 목적입니다.

1. 내 상황에서 무엇을 맡길 수 있나?
2. 이 스튜디오가 실제로 만든 제품은 무엇인가?
3. 시작하면 어떤 순서로 일하고 무엇을 확인하게 되나?
4. 문의할 때 무엇을 준비하면 되나?

### 기존 판단에서 갱신할 사항

- PreviewLog 자료를 확보하지 못한 상태에서 벗어났습니다. 현재 경로는 `/Users/macsk/Projects/previewlog-landing/deploy/index.html`입니다. 다른 `site/` 시안으로 대체하지 않습니다.
- PreviewLog 공개 주소는 이번 확인에서 HEAD 요청에 HTTP 404를 반환했습니다. 공개 페이지를 정상 열람하지 못했으므로 외부 CTA는 재검증이 필요합니다. 이 응답만으로 실제 제품의 출시 여부를 단정하지 않습니다.
- 확보한 랜딩의 `#download`는 설치파일 공개 준비 상태이고 대기자 폼의 `data-endpoint`는 비어 있습니다. “지금 다운로드”, “출시 알림 등록”은 작동 여부 확인 전 회사 사이트 CTA로 쓰지 않습니다.
- 따라서 홈의 “직접 만들고 출시한 제품”은 **“직접 만드는 제품, 구체적인 경험.”**으로 변경 제안합니다. Shuffo의 출시 사실과 PreviewLog의 공개 준비 상태를 구분합니다.
- 기존 로드맵의 모바일 메뉴 항목은 너무 넓게 표현되어 있습니다. Contact CTA와 Works 본문 링크는 남아 있지만 모바일의 주 메뉴와 About·Services 이동 경로가 부족한 것이 정확한 문제입니다.
- Workers·D1·관리자 인증을 일괄 “출시 후”로 미루는 기존 로드맵은 문의 폼 운영 목표와 충돌합니다. 정식 폼을 공개하는 경우 저장·조회·인증·개인정보 안내가 먼저 준비되어야 합니다.

### 홈 순서 변경 이유

기존 기획서의 Positioning을 앞에서 길게 반복하는 대신 Works를 Hero 다음에 배치합니다. 실제 제품으로 관심을 만든 다음, 구매 가능한 서비스와 협업 방식으로 연결하는 안입니다. 기존의 `MOVE FAST / MAKE IT SOLID / FROM IDEA TO LAUNCH`는 Process 소개의 짧은 원칙으로 통합하고 About에서 자세히 설명합니다.

한글 제목·본문은 방문자의 판단을 돕고, 영문 제목·레이블은 브랜드 톤과 정보 구분에 사용합니다. 모든 블록을 큰 영문 슬로건으로 채우지는 않습니다.

## 4. 시각 구성 제안

### 유지할 사용자 결정

- 다크 배경과 현재 블루 포인트 `#35a9ff`.
- 공식 심볼·워드마크 SVG. 워드마크는 표시 단계에서 흰색 처리.
- 헤더: 심볼 높이 36px, 워드마크 높이 20px, 간격 6px.
- 푸터: 심볼 높이 25.2px, 워드마크 높이 14px, 간격 6px.
- 영문 헤드라인: Inter Tight 300, 자간 0.025em.
- 한글 헤드라인: Pretendard 600, 자간 -0.045em.

### 정보 밀도 개선

- 홈 Hero만 크게 사용합니다. 내부 페이지는 제목 아래 설명·관련 내용이 첫 화면에 함께 들어오도록 높이와 여백을 줄입니다.
- 본문은 16–18px, 충분한 줄간격, 한 문단 2–3문장으로 구성합니다. 긴 한글 문장을 거대한 h2로 표시하는 현재 About 구조를 나눕니다.
- Services는 데스크톱 3개 주요 영역, 모바일 세로 배열로 구성합니다. 고객 상황·제공 범위·산출물의 위계를 구분합니다.
- Process는 데스크톱 4열, 태블릿 2열, 모바일 1열을 제안합니다.
- 긴 영문은 지정 자간을 유지하면서 글자 크기와 줄바꿈으로 폭에 맞춥니다. 단어 잘림과 가로 스크롤은 허용하지 않습니다.
- 반복되는 큰 카드 대신 서비스 목록, 단계별 진행표, 제품 화면 등 정보 성격에 맞는 구성을 씁니다.

## 5. 정보와 문구의 승인 기준

카피 초안은 다음 상태를 구분합니다.

- **기존 근거 있음:** 기획서·보유 자료·공식 제품 설명에 근거한 원고. 전체 문구 승인은 별도입니다.
- **운영 방식 승인 필요:** 산출물 제공, 작업 공유, 견적·유지보수 등 실제 영업 방식과 맞아야 하는 문구.
- **제품 검수 필요:** PreviewLog의 실제 구현·공개 상태와 일치하는지 확인할 문구.
- **입력값 필요:** 개인정보 관련 정보처럼 실제 값이 없으면 게시할 수 없는 부분.

고객명, 고객 후기, 다운로드 수, 누적 프로젝트 수, 속도 향상률, 최소 가격, 특정 납기, 상시 지원은 자료가 없는 상태로 추가하지 않습니다. 자체 제품과 외부 고객 의뢰 사례도 구분합니다.

## 6. 문의 기능의 두 단계

### 콘텐츠 승인 후 프리뷰 단계

현재 이메일 경로를 유지하면서 Q01·Q02·Q04의 준비 안내와 FAQ를 적용합니다. “정식 문의 폼은 운영 인프라 확정 후…” 같은 개발 진행 문구는 고객에게 필요한 문의 안내로 바꿉니다. 이 단계는 콘텐츠 검토용이며 정식 폼 완료로 표시하지 않습니다.

### 정식 문의 운영 단계

Q03의 폼과 상태 문구를 실제 기능에 연결합니다. 아래 두 변경은 승인 요청 사항입니다.

1. **회사명 필수 → 선택**을 제안합니다. 개인창업자에게 `개인` 입력을 강제하지 않기 위함입니다. 승인 시 검증·DB 필수 여부·고지 문구도 함께 바꿉니다.
2. **첨부파일은 후속 단계**를 제안합니다. 최초 문의는 설명과 참고 URL로 받고, 업로드가 준비되면 기존 기획의 3개·파일당 10MB 제한을 적용합니다. 1차부터 필요하면 공개 전 R2 보안 흐름까지 구현합니다.

예산·일정은 `협의 필요`와 `미정`을 유지합니다. 예산 선택지는 견적 가격표가 아닙니다. 단가·납기·회신 기한을 새로 약속하지 않습니다.

정식 폼 공개 조건: 서버 검증·스팸 방어·문의 저장·알림 실패 처리·인증된 운영자 조회·동의 및 개인정보 안내 일치·실제 테스트 문의 확인. 관리자 경로를 만들 경우 인증도 동시에 적용합니다. 공개 사이트와 폼을 한 번에 출시할지, 이메일 문의 사이트부터 공개할지는 사용자 결정입니다.

## 7. 구현 순서와 완료 기준

| 단계 | 실행 내용 | 완료 기준 | 의존성 |
| --- | --- | --- | --- |
| 0. 원고 승인 | 섹션·카피·제품 상태·운영 조건 확정 | 승인 ID와 보류 ID가 기록됨 | 사용자 컨펌 |
| 1. 공통 구조·홈 | 메뉴·제목 위계·서비스·Process·Studio·CTA | H01–H07 구현, 375/768/1280px에서 주요 경로 사용 가능 | 승인 원고 |
| 2. 상세 콘텐츠 | About·Services·Works 2개 상세·이미지 캡션 | A/S/W/P/G 원고와 근거 일치, 실제 이미지·목업 구분 | PreviewLog 검수·에셋 |
| 3. 문의 안내·운영 | 이메일 안내 개선 후 승인 범위의 폼/API/고지 | 성공·실패 안내가 실제 처리 결과와 일치 | 회사 정책·운영 정보 |
| 4. 공개 검수 | SEO·접근성·링크·이미지·전환 경로 | 빌드·타입·브라우저 QA 및 출시 체크 완료 | 앞 단계 |
| 후속 | 고객 사례·블로그·첨부파일(보류 시) | 공개 허가 및 운영 기능 준비 후 추가 | 실제 자료·별도 범위 확정 |

내용 구현 시 `src/data/site.ts`는 공통 정보, 서비스 데이터와 FAQ는 각각 공통 데이터, Works는 제품별 섹션·상태·갤러리를 표현하도록 확장합니다. 복사한 제품 소개 문구가 홈과 상세에서 따로 갱신되지 않게 합니다. 이 파일 구조는 구현 제안이며 이번 턴에는 코드 변경이 없습니다.

### 검수 기준

- 첫 화면에서 웹사이트·SaaS·앱을 만드는 스튜디오라는 사실과 문의 위치를 이해할 수 있음.
- 각 주요 서비스에 고객 상황·제공 범위·산출물 예시·다음 행동이 있음.
- PreviewLog의 기능 설명과 실제 배포 상태가 일치하고, 실패하는 외부 링크를 CTA로 노출하지 않음.
- Shuffo 화면의 핵심 내용이 크롭으로 잘리지 않고 읽을 수 있음.
- 모바일에서 모든 주 메뉴 접근 가능. 4단계 Process와 제목 줄바꿈 검수.
- 한글 제목 예외 스타일을 Works 제목 등 모든 해당 위치에 일관되게 적용.
- 문의 성공은 실제 서버 저장 확인 후 표시. 개인정보 고지의 미확정 값을 공개하지 않음.
- 각 페이지에 고유 title·description·canonical, OG, favicon 및 실제 공개 경로 기준 sitemap·robots 구성.
- `pnpm run check`, `pnpm run build`, 내부 링크 확인과 실제 화면 QA 실시.

전환 확인 항목은 메뉴/서비스→문의 이동, 제품 상세 열람, 이메일 클릭, 폼 시작·실제 접수 완료입니다. 이메일 클릭을 문의 접수로 집계하지 않으며, 분석 데이터에 이름·이메일·문의 내용은 넣지 않습니다. 수치 목표는 운영 기준값이 쌓인 뒤 정합니다.
