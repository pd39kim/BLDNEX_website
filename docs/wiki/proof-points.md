# 증거 요소 — 개발사임을 사이트가 직접 보여주는 장치

최종 갱신: 2026-10-05

## 왜 만들었나

"개발사의 웹사이트"라는 인상을 **문장으로 주장하지 않고 사이트 자체가 증명**하도록 세 가지를 넣었습니다. 모두 이미 가진 사실을 드러내는 것이고, 새로 만들어낸 주장은 없습니다.

| | 장치 | 위치 |
| --- | --- | --- |
| A1 | 빌드 실측 스탬프 | 홈 히어로 하단 |
| A2 | 이 웹사이트를 세 번째 작업물로 | `/works`, `/works/bldnex-website` |
| A3 | App Store 출시 배지 | 홈 Works 섹션 하단 |

---

## A1 — 빌드 실측 스탬프

홈 히어로 아래에 이 페이지의 실측 수치를 공개합니다.

```
THIS PAGE   용량 265 KB   JavaScript 0.6 KB   외부 요청 0건   빌드 2026-10-05
```

### 숫자를 손으로 적지 않습니다

`scripts/measure-site.mjs`가 빌드된 `dist`를 실측해 HTML의 토큰(`__PAGE_WEIGHT__` 등)을 채웁니다. 내용이 바뀌면 다음 배포에서 자동으로 갱신됩니다.

### 치환이 크기를 바꾸는 문제

토큰을 실제 값으로 바꾸면 HTML 크기가 수십 바이트 달라져, 표시된 숫자가 그 파일의 실제 값과 어긋납니다. 그래서 **치환 → 재측정을 값이 변하지 않을 때까지 반복**합니다. 5회 안에 수렴하지 않으면 빌드를 실패시킵니다. 덕분에 화면의 숫자는 그 파일 자체의 값입니다.

### 측정 정의

| 항목 | 기준 |
| --- | --- |
| 용량 | HTML·CSS는 gzip 압축 후, 폰트·이미지는 파일 크기 그대로 |
| JavaScript | 홈의 인라인 스크립트 바이트 (JSON-LD 제외). 번들 파일은 0개 |
| 외부 요청 | 0 — 폰트 셀프호스팅 후 서드파티 호스트가 없음 |
| 페이지 | `dist`의 HTML 파일 수 |

**실제보다 크게 잡습니다.** 홈이 쓰지 않는 글꼴 굵기(`pretendard-300`)까지 더하기 때문입니다. 브라우저 실측은 237 KB, 표시값은 265 KB로 표시값이 더 보수적입니다. 확인하는 사람이 보면 실제가 더 적게 나오는 방향이라, 숫자가 반박당하지 않습니다.

### 처음 제안은 틀렸습니다

원래 `11.2 KB · JS 0 KB`를 넣자고 했는데, 검증해 보니 HTML만 11 KB일 뿐 실제 로드는 **1.59 MB**였습니다. 98%가 외부 CDN에서 받던 Pretendard 전체 글꼴이었습니다. 그대로 공개했다면 개발자가 DevTools를 여는 순간 반박되는 주장이 됐을 것입니다.

그래서 **먼저 글꼴을 고치고**([웹폰트 문서](fonts.md)) 수치를 공개했습니다. 이 순서를 바꾸면 안 됩니다.

## A2 — 이 웹사이트를 세 번째 작업물로

`/works`에 PreviewLog·Shuffo와 나란히 **bldnex.com** 자체를 올렸습니다. "우리가 만든 걸 보시려면, 지금 보고 계신 게 그겁니다"가 가장 강한 증거이기 때문입니다.

상세 페이지 `/works/bldnex-website`는 네 부분입니다.

1. **실측 수치 4개** — A1과 같은 토큰을 쓰므로 홈과 항상 일치합니다. `check-site.mjs`가 두 값이 다르면 실패시킵니다.
2. **왜 중요한가** — 글꼴 1.59 MB를 발견하고 고친 경위를 그대로 적었습니다. 실패를 숨기지 않는 쪽이 설득력 있다고 판단했습니다.
3. **기술 구성** — Astro 5 / TypeScript / Cloudflare Pages / Sharp·subset-font. 유행하는 기술을 나열하지 않고 실제로 쓰는 것만.
4. **자동 검수 9개 항목** — `pnpm test`가 확인하는 내용을 공개합니다.

### 구현 메모

`[slug].astro`는 PreviewLog/Shuffo 2분기 구조라 세 번째를 끼워 넣으면 복잡해집니다. 전용 페이지 `works/bldnex-website.astro`로 분리하고, `getStaticPaths`에서 이 슬러그를 제외했습니다.

스키마는 `CreativeWork`입니다. `BaseLayout`이 사이트 전역 `WebSite`를 이미 내보내므로 한 페이지에 `WebSite`가 두 번 나오지 않게 했습니다.

카드는 그리드 2열에서 혼자 남지 않도록 전체 너비로 둡니다 (`.work-card-bldnex-website { grid-column: 1 / -1 }`).

## A3 — App Store 출시 배지

홈 Works 섹션 아래에 Shuffo의 실제 앱 아이콘과 **Apple 공식 한국어 배지**를 넣었습니다. "만들어 봤다"와 "출시해 운영 중이다"는 체급이 다르기 때문입니다.

### 앱 정보는 공식 API에서 받습니다

`scripts/fetch-appstore.mjs`가 Apple의 공개 lookup API에서 받아 `src/data/app-store.json`에 고정합니다. 성과 수치나 평점처럼 맥락에 따라 달라지는 값은 가져오지 않습니다.

```json
{ "name": "SHUFFO", "seller": "Sangkyu Kim", "genre": "Games",
  "minimumOs": "15.0", "releaseDate": "2026-09-26", "version": "1.2" }
```

빌드가 네트워크를 타지 않도록 결과는 커밋하고, 앱을 업데이트했을 때만 `pnpm assets:appstore`로 갱신합니다. 글꼴 원본과 같은 방식입니다.

`check-site.mjs`가 홈의 iOS 요구 버전과 앱 버전이 이 JSON과 일치하는지 확인하므로, JSON만 갱신하고 화면 문구를 안 고치면 빌드가 실패합니다.

### 에셋

| 파일 | 출처 | 크기 |
| --- | --- | --- |
| `app-icon.webp` | iTunes API의 512px 아트워크를 192px webp로 | 8.1 KB |
| `app-store-badge-ko.svg` | Apple Marketing Tools 공식 한국어 배지 | 9.3 KB |

배지는 Apple 상표이므로 공식 배포본을 그대로 쓰고 임의로 그리지 않습니다. 자사 앱으로 연결하는 용도라 통상적인 사용입니다.

## 빌드 검사

`scripts/check-site.mjs`가 매 빌드마다 확인합니다.

- 모든 페이지에 실측 토큰이 남아 있지 않은지 (= `measure-site`가 실제로 돌았는지)
- 홈의 외부 요청 수치가 `0건`인지
- 홈과 상세 페이지의 용량 수치가 같은지
- 표시된 페이지 수가 실제 라우트 수와 같은지
- 홈에 App Store 링크가 있고 `target="_blank" rel="noopener noreferrer"`인지
- 앱 아이콘과 배지 파일이 실제로 있는지
- 홈의 iOS 버전·앱 버전이 `app-store.json`과 일치하는지

## 유지보수

| 상황 | 할 일 |
| --- | --- |
| 사이트 내용 수정 | 없음 — 빌드가 수치를 다시 잽니다 |
| 페이지 추가 | 없음 — 라우트 수가 자동 반영됩니다 |
| Shuffo 업데이트 | `pnpm assets:appstore` 후 커밋 |
| 검수 항목 추가 | `works/bldnex-website.astro`의 `checks` 배열에도 추가 |

`checks` 배열은 사람이 적는 목록이라 실제 검사와 어긋날 수 있습니다. 검사를 추가할 때 이 배열도 같이 고쳐야 합니다.
